# Vespasian test infrastructure (agent reference)

Relocated from AGENTS.md (ENG-6805). How to run the suite: test/README.md.

## Test Infrastructure

The `test/` directory contains live test targets:

- **test/rest-api/**: Go HTTP server exposing REST endpoints for end-to-end testing
- **test/soap-service/**: Go HTTP server exposing SOAP/WSDL endpoints
- **test/graphql-server/**: Node.js GraphQL server with Apollo
- **test/grpc-server/**: Go gRPC server with Server Reflection enabled (sample User/Order/Account services, including a streaming method) for reflection-probe testing
- **test/concat-spa/**: Go HTTP server serving a single-page app whose API endpoints exist only as concatenated strings in an external JS bundle (discovered via post-crawl JS-replay)
- **test/forms-target/**: Go HTTP server serving an HTML `<form>` page whose POST endpoints are recovered by static form extraction (`analyze.ExtractForms`); a co-located GET search form contributes query parameters to a crawl-linked endpoint
- **test/internal/target/**: shared listener setup for the Go live-test targets. `Addr()` resolves the bind address (loopback by default, widened only via `BIND_HOST`) and `Server()` applies the read-header and companion timeouts. The four HTTP Go targets above (rest-api, soap-service, concat-spa, forms-target) each carried a byte-identical copy of both before this was consolidated. grpc-server is not among them: it binds a gRPC listener directly and keeps its own hardcoded loopback literal, so the loopback default — a security control for these unauthenticated fixtures — is now asserted in one place instead of four.
- **test/proto-validate/**: Go command that compiles a generated `.proto` in-process via `bufbuild/protocompile`; the grpc-server target's AC4 compile assertion (LAB-2778) shells out to it with `go run`, replacing the `command -v protoc` gate that always skipped (LAB-5549). Structurally the twin of `test/spec-validators/` below — a real-parser validator the live suite shells out to rather than grepping — but Go and in-process, so it needs no install step. It reports 0 when the spec compiles, 1 with the diagnostic on stderr when it does not, and 2 on bad arguments; `run()` is split from `main()` so those three exit paths are unit-tested rather than only exercised through the shell.

  It is the repo's one **nested Go module** (`test/proto-validate/go.mod`), and deliberately NOT joined by a `go.work` — a workspace would put this helper into the product's MVS build list, so a bump to its manifest could move the shipped binary's dependency set, and the security scan (which resolves at the repo root) could then report on a graph above the one that ships. `go.work`/`go.work.sum` are gitignored for that reason; every consumer enters the module with `cd`/`working-directory` instead. The reason is the dependency contract, not the code: `test/proto-validate` is `package main` inside the shipped module, so leaving it there made `bufbuild/protocompile` (and `golang.org/x/sync`) DIRECT requirements of `github.com/praetorian-inc/vespasian`, and every downstream consumer of `pkg/sdk` resolved and downloaded them for a helper that only validates live-test output. Splitting it keeps the root `go.mod` and `go.sum` untouched by this tool. The other Go live targets (`rest-api`, `soap-service`, `concat-spa`, `grpc-server`, `forms-target`) deliberately stay in the main module — their dependencies (grpc, protobuf, stdlib) are already product dependencies, so isolating them would buy nothing.

  The cost is that a root `go test ./...` / `go vet ./...` does NOT reach a nested module — a package pattern stops at the module boundary even inside a workspace. So each consumer names the module explicitly. The authoritative list is whatever
`grep -rn 'cd test/proto-validate' Makefile` and `grep -rln 'working-directory: test/proto-validate' .github/workflows/` return — do not trust a count written here, which has been wrong every time it was hand-maintained. Today that is four `Makefile` targets (`test`, `vet`, `lint`, `deps`) plus two CI jobs: `ci.yml`'s `proto-validate-tests` and `security.yml`'s `proto-validate-security` (govulncheck + gosec). Both jobs exist because the reusable workflows the `ci` and `security` jobs delegate to cannot be told about a second module, and both workflows needed the nested `go.mod`/`go.sum` in their `paths:` filters because the root-scoped patterns do not match them. If you add another nested module, wire it into every one of those — run the two greps above to enumerate them — or its tests will silently stop running and its dependencies will go unscanned.
- **test/spec-validators/**: private, pinned npm package (`package.json` + committed `package-lock.json`) holding the real-parser spec validators that `test/validate.sh` shells out to — `validate-openapi.mjs` (`@apidevtools/swagger-parser`) and `validate-graphql.mjs` (`graphql-js`). Install once with `(cd test/spec-validators && npm ci --ignore-scripts)`; after that it is fully offline, so the only egress is the `npm ci` fetch from `registry.npmjs.org`. It replaced the previous grep/substring-based spec validation (LAB-3890 T1), which false-passed malformed specs that merely *contained* the right strings. `test/validate.sh` fails the run with a clear "run: npm ci" message if the deps are missing.

`test/validate_test.sh` is the regression test that locks in those validators' reject behaviour: it asserts valid specs still pass and that every malformed / substring-trap fixture is rejected (e.g. an expected `GetUser` SOAP operation must no longer be satisfied by `GetUserList`). It needs only node plus the installed `test/spec-validators` deps — no Go build and no live services — and runs in about a second.

Supporting scripts: `test/install-chrome.sh` provisions a real non-snap Chrome for containers (Ubuntu's `chromium-browser` is a snap stub that cannot run in-container), installing it from Google's apt repo with the signing key pinned by fingerprint and the repo removed again afterwards. It is wired into `.devcontainer/Dockerfile` as an image layer (LAB-5766), so a fresh devcontainer comes up with a runnable browser and no manual step; the same Dockerfile installs `python3`, a SHA-pinned `yq`, Node 20, and Go 1.27.0 (yq and Go pinned by SHA-256 for both architectures) — the four prerequisites the base image lacks or ships too old. Node is the surprising one: the base image's metadata label lists the node devcontainer feature, but nvm's `versions/` directory is empty, so no version is installed and `$NVM_DIR/current` dangles. Measured from a build log, after two attempts that assumed npm was present failed with `npm: not found`. Node 20 matches the `actions/setup-node` version the CI jobs use, so the container and CI parse specs with the same runtime. `.devcontainer/devcontainer.json` carries the repo-root build context the layer's `COPY test/...` needs, sets `VESPASIAN_NO_SANDBOX`, and its `onCreateCommand` runs `npm ci --ignore-scripts` for `test/spec-validators` — that one cannot be an image layer, because the workspace is bind-mounted over the image's copy of it, so anything npm installs into the workspace path at build time is shadowed the moment the container starts. That layer names `container=docker` deliberately: `in_container()` gates the removal *and* the verify-absent pass over the package's phone-home artifacts, and none of the markers it reads (`/.dockerenv`, `REMOTE_CONTAINERS`) is a dependable build-time signal, so without it the build would suppress those artifacts without ever confirming their absence. Three CI jobs execute the installer — `install-chrome-e2e` directly, and `devcontainer-image` and `devcontainer-image-arm64` through the image build, since the Dockerfile COPYs and RUNs it (a fourth, `preflight-selftest`, only syntax-checks it). The opt-in `install-chrome-e2e` covers its privileged path in a bare `ubuntu:24.04` container, and `devcontainer-image` builds the devcontainer and re-runs `assert-chrome-install.sh` against the result, which is the only thing standing between the wiring and silent rot. `test/assert-chrome-install.sh` holds the post-install assertions the `install-chrome-e2e` job runs against a real install — a committed script rather than an inline `run:` block precisely so the un-gated `bash -n` step can see it, which an inline block is invisible to. `test/preflight-selftest.sh`, `test/test-runner-args.sh`, `test/install-chrome-selftest.sh`, and `test/setup-live-targets_test.sh` are the CI-run regression guards for the setup preflight, the target-group/dispatch wiring (plus the un-gated job's own step list and the browser-target classification), the installer's non-privileged surface, and the setup script's teardown / orphan-process hardening (LAB-2893). All four run in the un-gated `preflight-selftest` job, which the `test` job depends on so a guard failure stops the full suite before it builds anything.

`test/check-docs.py` guards the community-health docs (LAB-5870): the required root set exists, every relative markdown link and heading anchor resolves, reference-style link definitions and usages correspond (the Keep a Changelog shortcut references in `CHANGELOG.md`), and the `*` owner line in `CODEOWNERS` matches the maintainer table in `GOVERNANCE.md`. It exists because `GOVERNANCE.md` and `SUPPORT.md` were absent from `main` for a week — two stacked PRs merged into feature branches that nothing merges from again — and no check noticed; run against that commit it fails on both files. Python rather than shell because the link and anchor logic needs real parsing and these scripts are authored on macOS to run on Linux, where the `sed`/`grep`/`stat` flag sets diverge in both directions. Wired into `make check` and run in CI as the ungated `docs-check` job.

See `test/README.md` for how to run the suite, including the `TEST_HOST` override for devcontainer setups, the browserless `--group offline` path, and the `//go:build integration` browser-lifecycle tests.
