# Vespasian CI (agent reference)

## CI

GitHub Actions runs on push to main and PRs:

- **ci.yml**: Build, test (`go test -race`), an 85% statement-coverage gate (`make coverage-gate`), lint (golangci-lint v2), and format check. Runs on every push to `main`, and on PRs to `main` whose changes match its `paths` filter — the filter is nested under `pull_request` only (so pushes are unfiltered), and it covers `**/*.go`, `go.mod`, `go.sum`, `test/proto-validate/go.mod`, `test/proto-validate/go.sum`, `.golangci*`, `Makefile`, and `scripts/**`, not Go files alone. It delegates to a shared reusable workflow whose inputs are all `build-*` (see the `with:` block), so today it passes no build tag — integration-tagged tests run from live-tests.yml instead, and the coverage gate is a separate job for the same reason.
- **live-tests.yml**: ten jobs — three un-gated guard jobs, an opt-in end-to-end installer job, a devcontainer paths filter, the devcontainer image build and its arm64 build-only leg, a label gate, the integration-tagged Go suite, and the full suite.

  **`preflight-selftest`** (un-gated) is the shell regression net. It runs a `bash -n` syntax check (over `setup-live-targets.sh`, `install-chrome.sh`, `assert-chrome-install.sh`, `assert-devcontainer-lookpath.sh` and `.devcontainer/on-create.sh` — `test-runner-args.sh` asserts every committed `test/assert-*.sh` the workflow execs is in that chain, so adding one of those cannot silently escape syntax coverage; note the guard is scoped to `test/assert-*.sh`, so `.devcontainer/on-create.sh`'s place in the chain rests on this enumeration rather than on an assertion) and then all four guard suites: `test/preflight-selftest.sh` (Chrome/Chromium detection, LAB-3893), `test/install-chrome-selftest.sh` (the installer's non-privileged surface), `test/setup-live-targets_test.sh` (teardown / orphan-PID hardening, LAB-2893), and `test/test-runner-args.sh` (target-group vs dispatch drift, the un-gated job's own step list, browser-target classification, and two further guards: the `test` job is excluded from the gated-job allowlist, so a suite hosted only there cannot satisfy the wiring check while staying skippable via `skip-live-tests`, and `install-chrome-e2e`'s verification steps are pinned by name so deleting one fails CI). None need Go, Node, or Chrome. A further step re-runs `test/test-runner-args.sh` with `yq` removed from `PATH` and fails on `assertion accounting drift`: every block with a vacuity sentinel must credit exactly the counted outcomes its other arm does not emit, and getting that wrong is green on CI (which ships `yq`) while misreporting on a contributor's machine. It refuses to run vacuously — it asserts `yq` resolves normally, does NOT resolve on the stripped `PATH`, that the yq-gated arms were actually reached, and that every failure is one of them. `test-runner-args.sh` fails CI if a dispatch target is not covered by `OFFLINE_TARGETS` or `LIVE_TARGETS` (there is no config-only tier: it existed for `grpc-server` alone and its only effect was to exempt that target from the coverage check, which is why the epic's headline gRPC target ran on no PR until LAB-5549 moved it into `LIVE_TARGETS`), if this job stops invoking one of the four suites, or if a target in `ALL_TARGETS` is classified neither browser nor non-browser.

  **`validator-regression`** (un-gated) does its own `npm ci --ignore-scripts` in `test/spec-validators` and runs `./test/validate_test.sh` to prove the spec validators still reject malformed specs.

  **`docs-check`** (un-gated) runs `python3 test/check-docs.py --verbose` (LAB-5870): the required community-health docs exist, every relative markdown link and heading anchor resolves, reference-style link definitions and usages correspond (the Keep a Changelog shortcut references in `CHANGELOG.md`), and the `*` owner line in `CODEOWNERS` matches the maintainer table in `GOVERNANCE.md`. It lives in this workflow rather than `ci.yml` because `ci.yml`'s `paths` filter (on `pull_request` only, and covering Go sources, `go.mod`/`go.sum`, `.golangci*`, `Makefile`, and `scripts/**`) does not list Markdown — a docs-only PR never triggers it, so the job guarding docs must not be gated on it.

  All three guard jobs (`preflight-selftest`, `validator-regression`, `docs-check`) sit deliberately **outside** the label gate, so `skip-live-tests` cannot switch off the regression net. All three have ~5-minute timeouts.

  **`install-chrome-e2e`** exercises the installer's PRIVILEGED path — the download, the signature-verified apt install, the trap teardown, and the AC4 cleanup that runs after the package's postinst. It is opt-in (`workflow_dispatch`, plus every push to `main`) rather than per-PR, because it needs root, real egress to Google, and it mutates system state; it runs as root in a disposable digest-pinned `ubuntu:24.04` container, so those mutations are thrown away. It asserts a runnable browser, absent phone-home artifacts, a version record, and an idempotent second run. `install-chrome-selftest.sh` covers every rejection arm unprivileged but stops before the first `$SUDO`, so without this job that region had no automated coverage at all.

  **`devcontainer-image`** is what stops the devcontainer wiring rotting. It builds the image **through `devcontainer.json`** using `@devcontainers/cli` (pinned) rather than a hand-written `docker build`: re-specifying the build by hand left the file every developer's "Reopen in Container" actually consumes unparsed, so its `context`, `containerEnv`, `runArgs` and `remoteUser` were all unasserted and breaking any of them changed no signal in this repo. It then `devcontainer up`s the container — which applies `VESPASIAN_NO_SANDBOX`, `--shm-size=1g` and `remoteUser: vscode`, and runs the `onCreateCommand` that installs the spec-validator deps — and runs every assertion through `devcontainer exec`, so the configuration under test is the one developers get rather than root with none of it. Six exec-based assertions, all through `devcontainer exec`: a conformance step that checks the container the file actually produced (`id -un` is `vscode`, `VESPASIAN_NO_SANDBOX` set, `/dev/shm` >= 1GB, the spec-validator ENTRY POINTS the `onCreateCommand` installs — the same check `_ensure_spec_validators` makes, not a bare `-d node_modules` — and that the image's Go satisfies `go.mod`, read from `go.mod` rather than pinned to a literal, after the image shipped Go 1.25.12 against a `go.mod` requiring 1.27.0 and every Go step in the container died under `GOTOOLCHAIN=local`); `test/assert-chrome-install.sh` (the shell probe, which executes the binary); `test/assert-devcontainer-lookpath.sh` (go-rod's `LookPath` **plus** the four `TestBrowserManager_*` launch/kill/close tests LAB-5064 AC1 actually names — filtering to the `LookPath` test alone asserted resolution and called it launch coverage), the two guard suites, which is what catches a missing prerequisite; and the AC3 step, which runs `./test/setup-live-targets.sh && ./test/run-live-tests.sh --no-build --group live` INSIDE the image and then requires the rod-backed targets (`no-download`, `concat-spa`, `forms-target`) to report PASS rather than SKIP — the exit code alone cannot say that, because run-live-tests.sh only fails an all-skipped run when the WHOLE selection skipped and `LIVE_TARGETS` mixes rod-backed with plain-HTTP targets. On the prerequisite point: `test-runner-args.sh` routes to `fail()` rather than `skip()` without `yq`, so a `yq`-less image fails a whole suite the un-gated `preflight-selftest` job runs on every PR (deliberately no figure here: the count tracks the suite's size and has gone stale twice already — the invariant is that the guard routes to `fail()`, not `skip()`, so the failures are COUNTED and the accounting pin still reconciles). Both assertion scripts are committed FILES, not inline `run:` blocks, so the un-gated `bash -n` step can see them — an inline block is not a file, and run 32388761616 lost two steps to exactly that. The build step greps the build log for install-chrome.sh's in-container marker, because a successful build is AC4's only proof and only that arm removes AND verifies-absent the phone-home artifacts; a third copy of the path list is the drift the existing two already demonstrated. Gated on three arms now — `workflow_dispatch`, push-to-main, and a `pull_request` filtered by `devcontainer-changes` — so a PR touching the image builds it before merge instead of breaking main. `test/test-runner-args.sh` pins the job the way it pins `install-chrome-e2e`: deleting its whole LookPath step used to leave that suite at 135/135 exit 0.

  **`devcontainer-changes`** is the paths filter the `pull_request` arm gates on. GitHub Actions has no per-job `paths` filter and this workflow must run on every PR (the un-gated guards depend on it), so the filter has to be a job whose output the image job reads. Scoped to `.devcontainer/**`, the scripts the image copies, `.dockerignore` and this workflow (both govern the build context), and `go.mod` — the conformance step compares the image's toolchain against it, so a PR whose only change is the `go` directive must run this job, which is exactly the change that shipped an image two minor versions behind. The `git diff` runs with `--no-renames`, so a file moved OUT of a watched path is reported as a delete and still fires. An ordinary PR still pays nothing.

  **`devcontainer-image-arm64`** is a build-only leg. The Dockerfile's header and `devcontainer.json`'s premise both commit to arm64 working and the base image index does carry `linux/arm64`, but only `linux/amd64` was ever built, so the claim rested on registry inspection rather than on a build. No run steps: QEMU emulation is too slow to drive a browser through, and the failure it guards against is the layer not building at all — an arch-specific apt resolution, or the `yq` pin's arm64 digest going stale.

  **`check-label`** decides whether the two gated jobs (`integration-tests`, `test`) run: every PR by default, skipped when the `skip-live-tests` label is present; push to `main` and `workflow_dispatch` always run.

  **`integration-tests`** runs `make test-integration` (`go test -race -tags=integration ./...`) against the runner's stable Chrome, ~170s. It sets `VESPASIAN_REQUIRE_CHROME: "1"`, which turns `skipIfNoChrome`'s skip into a failure: without it a browserless runner skipped every rod row and `make test-integration` exited 0, which is indistinguishable in the build output from a real pass, and the browser-only assertions the job exists for are exactly the ones that vanish. Developers without a browser keep the skip by not setting the variable (LAB-4678 review). It exists because nothing passed `-tags=integration` anywhere, so 24 tests across 4 files never executed in CI — including `TestCrawlerContract_ScopeConfinement` and `_DepthLimit`, the only end-to-end assertions of two crawl containment controls, plus the LAB-4678 tests pinning the exact `--max-pages` count and the `--interact` destructive-control gate. It is a separate job from `test` so a live-target setup failure and a browser-test failure stay distinguishable.

  **`test`** runs all targets via `test/run-live-tests.sh --group offline` then `--group live`, using the stable Chrome shipped with the ubuntu-24.04 runner. It declares `needs: [check-label, preflight-selftest]` — the second dependency is fail-fast, not decoration: the shell guards used to be this job's first step, and depending on the job restores that behaviour, so a drift failure stops the run before it builds Go, starts six services, and crawls with a browser. It does `npm ci --ignore-scripts` in `test/spec-validators` (via `actions/setup-node` with `cache: npm` keyed on `test/spec-validators/package-lock.json`) because the offline `generate-{rest,graphql,wsdl}` targets validate output with real parsers rather than grep. No stub config is written before the offline run: `run-live-tests.sh` loads `.live-test-config` only for targets that talk to a live service, so the offline group exercises the same no-config path a developer gets on a fresh checkout. Target groups are defined in `test/run-live-tests.sh` — the workflow references groups, not individual targets, so adding a target means editing one array in the runner.

  Eight of the nine non-container jobs (`preflight-selftest`, `validator-regression`, `docs-check`, `devcontainer-changes`, `devcontainer-image`, `devcontainer-image-arm64`, `integration-tests`, `test`) open with a `step-security/harden-runner` step in `egress-policy: audit` mode (LAB-4732) — defense-in-depth network monitoring that logs (does not block) outbound traffic; `registry.npmjs.org` is part of the anticipated allowlist. The one that does not is `check-label`, a pure gate that runs no code and makes no egress. `devcontainer-image-arm64` DOES carry it, despite building nothing it keeps: the build COPYs and runs `test/install-chrome.sh` as root, reaching dl.google.com for the Chrome package and github.com for the pinned yq binary, so emulated or not it performs the same third-party egress as root that its amd64 sibling does. `install-chrome-e2e` is the one CONTAINER job and carries none because the action does not support container jobs, which matters because it is the one job running as root with live egress to Google's apt repo. The `--ignore-scripts` flag on every npm install — the two in this workflow and the `onCreateCommand` in `.devcontainer/devcontainer.json` — blocks npm lifecycle scripts from executing under the non-blocking audit-only egress policy. `test/test-runner-args.sh` derives every one of these numbers from the workflow and asserts it: the harden-runner copy count against BOTH number-words in this sentence and against the lockstep comment's own word, and that every copy pins the SAME sha across this file and ci.yml.
